# 第 13 章：完整系統整合 — 一鍵啟動、七步驟驗證、看見全貌

> 最後一章不學新東西，而是把你學過的**全部東西一次跑起來**：一個 compose 啟動 13 個容器，然後用一套七步驟的驗證流程證明整條 pipeline 是通的。這套驗證方法本身，就是你帶得走的資產。

---

## 做完這一章，你會做到

1. 用 `docker-compose-all.yml` 一個指令啟動全部服務（13 個容器）。
2. 跑完七步驟端到端驗證：服務 → Web → logs → 發任務 → 執行 → 資料 → 編排。
3. 對照全架構圖，說得出每個服務在系統裡的角色。
4. 建立「驗證一個多服務系統」的標準流程——不是「容器有起來」就叫成功。

## 一步一步跟著做

### 準備

先確認 image 存在、並把其他 compose 關掉，避免 port 衝突。「Step 1~7」這組編號留給下面的驗證流程專用，準備和啟動不佔編號：

```bash
# 確認 stock-airflow image 在（第 10 章 build 過）
docker images | grep stock-airflow
# 沒有就 build：docker build -f airflow/Dockerfile -t stock-airflow:latest .

# 其他 compose 全部先關掉，避免 port 衝突
docker compose -f docker-compose-local.yml down 2>/dev/null
docker compose -f airflow/docker-compose-airflow.yml down 2>/dev/null

cp .env.example .env    # 沒有 .env 的話
```

### 啟動：一個指令起全部服務

```bash
docker compose -f docker-compose-all.yml up -d
```

等 60~90 秒讓所有服務就緒（Airflow init、MySQL 初始化、Metabase JVM 都要暖機）。

## 七步驟端到端驗證

> **為什麼要七步？** 因為「容器都是 Up」離「系統真的能動」還很遠。服務起來了但連不上、任務發了但沒人做、worker 跑了但資料沒進庫——每一種都是真實會發生的故障。七步驟就是逐層把「看起來會動」變成「證明會動」。

### Step 1：服務狀態

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}' | sort
```

> ✅ 全部 Up；`airflow-init` 是 `Exited (0)` —— 一次性初始化容器，跑完退出**是正常的**。

### Step 2：Web 介面

```bash
curl -s -o /dev/null -w "RabbitMQ:  %{http_code}\n" http://localhost:15672
curl -s -o /dev/null -w "Flower:    %{http_code}\n" http://localhost:5555
curl -s -o /dev/null -w "phpMyAdmin:%{http_code}\n" http://localhost:8080
curl -s -o /dev/null -w "Airflow:   %{http_code}\n" http://localhost:8081/health
curl -s -o /dev/null -w "Metabase:  %{http_code}\n" http://localhost:3000/api/health
```

> ✅ 五個都 200。Metabase 最慢（JVM），503 就再等 30 秒。

### Step 3：Logs 判讀

```bash
docker logs crawler_twse 2>&1 | tail -3     # 要看到 ready
docker logs crawler_tpex 2>&1 | tail -3     # 要看到 ready
docker logs airflow-init 2>&1 | tail -3     # 要看到 User "admin" created
```

> ✅ worker ready、admin 建好。
>
> 💡 判讀重點：啟動初期的 `Connection refused` 是**啟動順序**造成的暫時現象（worker 比 RabbitMQ 先跑），會自動重連——這不算錯誤。要區分「暫時的連線重試」和「真正的 error」。

### Step 4：發任務

```bash
uv run crawler/producer_multi_queue.py
```

> ✅ `send task_2330 task`、`send task_00679b task`。

### Step 5：Worker 執行

```bash
sleep 5
docker logs crawler_twse 2>&1 | grep succeeded | tail -3
docker logs crawler_tpex 2>&1 | grep succeeded | tail -3
```

> ✅ 兩個 worker 各自 `succeeded`——twse 做 2330、tpex 做 00679B（第 3 章的分流仍在運作）。

### Step 6：DB 驗證

```bash
docker exec mysql mysql -uroot -p1234 mydb -e \
  "SHOW TABLES; SELECT stock_id, COUNT(*) AS cnt FROM TaiwanStockPrice GROUP BY stock_id;"
```

> ✅ `TaiwanStockPrice` 存在、兩支股票各有數百筆。**任務 succeeded 還不夠，資料在庫裡才算數。**

### Step 7：Airflow 編排層

```bash
docker exec airflow-webserver airflow dags list 2>&1 | grep stock
```

> ✅ 列出 `stock_crawler_dag`、`stock_crawler_producer_dag`、`stock_crawler_etl_dag` 等。
>
> 開 http://localhost:8081（admin / admin），想跑就 unpause + trigger `stock_crawler_dag`，回 Step 6 再驗一次資料增長——那就是完整閉環。

## 卡住了？常見錯誤這樣排

| 你遇到的狀況 | 原因 | 怎麼解 |
|-------------|------|--------|
| worker 的 log 出現 Connection refused | worker 比 RabbitMQ 先啟動，RabbitMQ 還沒準備好 | worker 會自動重連，等幾秒就恢復，不需要處理 |
| Airflow UI 打不開 | init 的初始化還沒有跑完 | 先用 `docker logs airflow-init` 確認初始化完成，再執行 `docker restart airflow-webserver` |
| Metabase 回 503 | Metabase 是 JVM 應用，啟動比其他服務慢 | 等 30~60 秒再試一次 |
| port 被佔用 | 其他的 compose 還開著，跟這一套搶同一個 port | 回到「準備」段，先把其他 compose down 掉 |
| 報錯說 stock-airflow image 不存在 | 還沒有 build 過這顆 image | 執行 `docker build -f airflow/Dockerfile -t stock-airflow:latest .` |
| MySQL 裡沒有資料表 | 還沒有發過任何任務，worker 沒寫過資料 | 跑驗證的 Step 4 發一批任務；或載入 mock 資料：`docker exec -i mysql mysql -uroot -p1234 mydb < example/mock_stock_price_data.sql` |

## 想一想（確認你懂了）

**Q1：為什麼「容器全部 Up」不能當成「系統正常」的證明？**

Up 只代表行程存在，不代表：連得上彼此（網路對不對）、任務有人做（`-Q` 訂對了嗎）、資料寫得進（帳密 host 對嗎）。這一章的七步驟就是把這些斷點逐層驗掉——**驗證要驗到資料落地，不是驗到容器啟動。**

**Q2：`airflow-init` 顯示 Exited，該緊張嗎？**

看 exit code：`Exited (0)` 是一次性初始化容器的正常結局（做完就走）；`Exited (1)` 以上才是出錯。學會分辨「設計上就會退出的容器」和「掛掉的容器」。

**Q3：如果 Step 5 的 worker succeeded、但 Step 6 查不到資料，你會怎麼追？**

這是第 7 章排錯 SOP 的實戰：任務成功但資料不在，通常是「寫去了別的地方」——worker 容器裡的 `MYSQL_HOST` 指到哪？是不是連去了另一個 MySQL（例如本機那個）？查 worker 環境變數（`docker exec crawler_twse env | grep MYSQL`）、再查它 log 裡的連線資訊，把「寫到哪裡去了」找出來。

## 換你試試看

**練習 1：跑完整閉環（Airflow 版）**

在 Airflow UI（8081）unpause + trigger `stock_crawler_dag`，等它跑完，用 Step 6 的 SQL 確認 10 支股票的資料都增加了。這是「編排層驅動的端到端」——比手動 producer 又高一層。

**練習 2：接上 Metabase**

照第 8 章的方法在 Metabase（3000）加 MySQL 資料來源（Host 填 `mysql`），把剛爬的資料拉成走勢圖。至此：**排程 → 爬取 → 入庫 → 視覺化**，全部在同一組容器裡發生。

**練習 3：故障演練**

故意 `docker stop crawler_twse`，發一批 twse 任務，用第 7 章的 SOP 找出「症狀 → 原因」（提示：RabbitMQ 的 Ready 會堆）。然後 `docker start crawler_twse`，看任務被消化。這是整套系統的綜合排錯驗證。

## 全課程收束：整條 pipeline 的全貌

十三章走完（加上下一章的雲端延伸），整套系統長這樣：

```
Airflow（DAG 定時 + 依賴 + 補跑 + 監控）
   → Producer 發任務 → RabbitMQ 佇列 → Celery Worker 爬 FinMind
   → 寫入 MySQL（冪等 upsert）→ 同步 BigQuery（OLAP 分析，第 15 章）
   → Metabase 做成 Dashboard
外加：失敗自動 retry / requeue、Flower 監控、多佇列分流、排錯 SOP、
     以及執行引擎可以抽換——第 12 章示範過把 Airflow 的 executor
     從 LocalExecutor 換成 CeleryExecutor，一個環境變數就能水平擴充
```

- **Phase A（第 1~7 章）**：把「任務怎麼可靠地跑」徹底拆解——Celery、分流、失敗處理、落地、冪等、監控介面。
- **Phase B（第 8~9 章）**：資料的下游出口與自動化——視覺化與定時排程。
- **Phase C（第 10~13 章）**：用 Airflow 把所有東西編排成生產級工作流，最後整套整合。
- **延伸（第 15 章）**：把資料搬進雲端倉儲 BigQuery，銜接後續的雲端部署。

最後，試著從第 12 章的 Airflow DAG 往回看：每一個 Operator 背後，都是你前面某一章學過的東西。這種「回頭看見全貌」的一刻，就是整套課最有價值的收束。恭喜你走完了。
