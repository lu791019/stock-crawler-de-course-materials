## 先搞懂：什麼是「冪等」

**打個比方**：電梯的「5 樓」按鈕，你按一次是去 5 樓，連按五次還是去 5 樓——**多按沒有副作用**。這就是冪等：同一個操作做幾次，結果都一樣。

上一章的寫法**不冪等**：每跑一次就 `append` 一批，跑三次就三份重複。但真實情況每天都會重抓、失敗會重試、補資料會重跑，**不冪等的 pipeline 會越跑越髒**。

解法：讓「同一筆資料」有一個唯一身分（主鍵），寫入時如果這筆已經存在就**更新**、不存在才**新增**。這個「有就更新、沒有就新增」的動作叫 **upsert**（update + insert）。

## DataFrame 與資料清理

**什麼是 DataFrame**：

- DataFrame 是 Python 套件 pandas 的核心資料結構，可以想像成「**強化版的 Excel 表格**」
- 由**列（rows）**和**欄（columns）**組成，支援不同型態的資料（數字、文字、時間…）
- 專為資料處理設計，能幫你：讀取各種資料來源 (`read_sql`、`read_csv`)、檢查與清理資料品質、篩選/轉換/聚合、輸出結果（`to_sql`、`to_csv`）

**空值處理的心法**：

- **爬蟲時就做好防呆、預設值處理**——API 回來的資料可能缺欄位、缺值，越早處理越省事
- 資料還是 list of dict 時要**逐筆**處理，比較沒效率
- 轉成 DataFrame 就能**統一處理**：查看/處理單一欄位、新增/刪除欄位、篩選查詢

## 一行一行讀懂「去重寫入」

### 第一步：定義資料表結構，指定複合主鍵

```python
from sqlalchemy import BigInteger, Column, Date, Float, MetaData, String, Table

metadata = MetaData()
stock_price_table = Table(
    "TaiwanStockPrice_duplicate",                      # 資料表名稱
    metadata,
    Column("stock_id", String(50), primary_key=True), # 主鍵之一
    Column("date", Date, primary_key=True),           # 主鍵之二
    Column("Trading_Volume", BigInteger),
    Column("open", Float),
    Column("max", Float),
    Column("min", Float),
    Column("close", Float),
    # ...其餘欄位
)
metadata.create_all(engine)   # 表不存在才建立
```

**最關鍵的一句**：`stock_id` 和 `date` 兩個欄位都設了 `primary_key=True`，這叫**複合主鍵**。意思是「同一支股票、同一天」在這張表裡只能有一筆——這就是每筆資料的「唯一身分」。上一章的表沒有主鍵，所以資料庫根本不知道哪兩筆算「重複」；這一章明確告訴它了。

### 第二步：upsert——重複就更新，不重複就新增

```python
from sqlalchemy.dialects.mysql import insert   # MySQL 專用的 insert，支援 on_duplicate_key_update

for _, row in df.iterrows():
    # ① 準備插入這一列
    insert_stmt = insert(stock_price_table).values(**row.to_dict())

    # ② 如果主鍵撞到已存在的資料，就改成「更新所有欄位為新值」
    update_stmt = insert_stmt.on_duplicate_key_update(
        **{col.name: insert_stmt.inserted[col.name]
           for col in stock_price_table.columns}
    )

    # ③ 執行
    with engine.begin() as conn:
        conn.execute(update_stmt)
```

一段一段看：

- **① `insert(...).values(...)`**：準備把這一列（`row`）插入表裡。
- **② `.on_duplicate_key_update(...)`**：這是**MySQL 專用語法**，也是整章的靈魂。它的意思是——「如果這筆的主鍵（stock_id + date）跟已存在的撞到了，別報錯、別製造重複，改成把那些欄位更新成新值」。那個 dict comprehension 就是在說「所有欄位都更新成新值」。
- **③ `with engine.begin() as conn`**：在一個交易（transaction）裡執行，確保寫入的完整性。

所以無論這支任務跑幾次，`TaiwanStockPrice_duplicate` 裡「同股同日」永遠只有一筆，而且是最新的值。**這就是冪等。**

> 對照上一章：那邊用 `to_sql(if_exists="append")`，沒有主鍵概念，只會一直往後疊；這一章用明確的複合主鍵 + upsert，才真正做到冪等。

## 反向驗證：有主鍵的表，遇上 append 會怎樣？

本章把表加上了複合主鍵、寫入換成 upsert。那如果**只做一半**——表有主鍵、但寫入還是用第 5 章的 append 版（`crawler_finmind`）呢？

| | 表**沒有**主鍵（第 5 章）| 表**有**主鍵（本章起）|
|---|---|---|
| **append**（普通 INSERT）| ✅ 永遠成功——但重跑翻倍（沒人擋）| 第一輪 ✅；**第二輪 ❌ 撞 1062 任務炸掉** |
| **upsert**（ON DUPLICATE KEY UPDATE）| ✅ 成功，但備案永遠不觸發（形同 append）| ✅ 撞主鍵→改更新——完全體 |

為什麼第二輪必炸：append 版任務每次執行都「從 2024-01-01 抓**整段歷史**塞一遍」，第二輪塞的資料大部分表裡已經有了——主鍵拒收、報 `ERROR 1062`、整個任務失敗（VM 實測過，錯誤訊息見補充D 分區節）。

三個容易混淆的點，一次釐清：

- **這跟分區無關**：普通表加上主鍵，效果一模一樣。補充D 的分區實驗會踩到它，只因 MySQL 規定「分區鍵必須在主鍵裡」——分區逼你裝主鍵，主鍵才是引爆點。
- **這跟 Python 或 SQL 無關**：主鍵只看「進來的資料」，不看誰發的 INSERT。用 SQL 搬舊資料撞 1062，是因為**舊表內部本來就有重複**（append 塞出來的），搬家時自己撞自己——所以搬遷用 `INSERT IGNORE` 跳過。
- **成對原則**：`crawler_finmind`（append）只能配「沒主鍵的表」；表一旦有主鍵——不管是為了防重複還是為了分區——寫入端就必須換 `crawler_finmind_duplicate`（upsert）。**表的設計和寫入的方式，永遠成對出現。**

## 想再深入一點

- **為什麼這一章要自己用 `Table(...)` 定義結構，第 5 章卻不用？** 因為 `on_duplicate_key_update`（upsert）要能運作，資料庫必須先知道「哪些欄位是主鍵」——它是靠「主鍵撞到了沒」來判斷該 insert 還是 update。第 5 章的 `to_sql` 自動建表不會幫你設主鍵，所以這一章改成明確用 `Table(...)` 宣告 `stock_id` + `date` 為複合主鍵，upsert 才有依據。
- **`insert_stmt.inserted[col.name]` 是什麼？** 這是 MySQL upsert 的慣用寫法，`inserted[...]` 代表「這次原本要插入的那個新值」。所以 `on_duplicate_key_update` 那段的意思就是「如果撞到主鍵，把每個欄位都更新成這次帶進來的新值」——等於用新資料覆蓋舊資料。
- **為什麼用 `iterrows()` 一列一列寫？慢不慢？** 慢。`iterrows()` 逐列跑迴圈、一列送一次 SQL，資料量大時效率不好。教學這樣寫是為了讓你看清楚「每一列都在做 upsert」的邏輯；正式環境會改成「批次 upsert」（一次送多列）來加速。你之後優化時可以往這個方向想。
- **換成別的資料庫呢？** `on_duplicate_key_update` 是 **MySQL 專屬**語法（所以 import 的是 `sqlalchemy.dialects.mysql.insert`）。如果換成 PostgreSQL，要改用 `ON CONFLICT (...) DO UPDATE`；概念一樣（upsert），但語法不同。這也是為什麼 import 要特別指定 MySQL 方言。
- **主鍵怎麼選是門學問。** 這裡選 `stock_id + date` 是因為它能唯一辨識「某股某日」這筆商業資料。換一種資料就要重想：例如「使用者的每日簽到」可能是 `user_id + date`、「訂單明細」可能是 `order_id + product_id`。選錯主鍵，冪等就會失效（要嘛擋不掉重複，要嘛蓋掉不該蓋的資料）。

## 想一想（確認你懂了）

先自己想過再看答案。

**Q1：用一句話解釋「冪等」，並舉一個生活例子。**

冪等 = 同一個操作做一次跟做很多次，結果一樣。生活例子：電梯樓層鍵（連按不會多帶你去幾層）、或「把開關撥到 ON」（撥幾次都還是 ON）。相對地，「再倒一杯水」就不冪等（做幾次就多幾杯）。

**Q2：為什麼 `stock_id` 單獨當主鍵不夠？為什麼要加 `date`？**

因為同一支股票有很多天的資料，如果只用 `stock_id` 當主鍵，2330 就只能存一筆，第二天的資料會把第一天蓋掉。要能「一支股票、多天各一筆」，唯一身分必須是「股票 + 日期」的組合，所以要用 `stock_id + date` 複合主鍵。

**Q3：如果 FinMind 事後修正了某天的收盤價，重跑這支任務會發生什麼？**

因為主鍵（該股該日）已存在，upsert 會走「更新」那條路，把那一筆的欄位**更新成新的收盤價**，而不是新增一筆。所以你的資料會被自動修正成最新值，且不會產生重複。這正是冪等在真實維運裡的價值。

## 這一章你學到了

- 冪等 = 同操作做幾次結果都一致，是定期資料流的必備性質。
- 複合主鍵定義「一筆資料的唯一身分」，upsert 讓重跑安全。
- MySQL 用 `on_duplicate_key_update` 實作 upsert。
