## 一行一行讀懂 `crawler_finmind_print`

```python
import pandas as pd
import requests
from crawler.worker import app

@app.task()
def crawler_finmind_print(stock_id):
    # ① FinMind API 的網址
    url = "https://api.finmindtrade.com/api/v4/data"

    # ② 你要問 API 的四個問題，包成一個 dict
    parameter = {
        "dataset": "TaiwanStockPrice",   # 我要哪種資料：台股日線
        "data_id": stock_id,             # 哪一支股票：例如 2330
        "start_date": "2024-01-01",      # 從哪天開始
        "end_date": "2025-06-17",        # 到哪天結束
    }

    # ③ 真正發出 HTTP GET 請求
    resp = requests.get(url, params=parameter)

    # ④ 把回傳的 JSON 轉成 Python dict
    data = resp.json()

    # ⑤ HTTP 200 代表成功
    if resp.status_code == 200:
        df = pd.DataFrame(data["data"])  # data["data"] 是 list of dict，直接變表格
        print(df)                        # 只印出，不寫 DB
    else:
        print(data["msg"])               # 失敗就印錯誤訊息，方便你排查
```

有沒有發現？**這就是你剛剛在熱身段落徒手做的事**，只是多了兩個差異：股票代碼變成參數 `stock_id`（誰派任務誰決定抓哪支），以及最上面多了一行 `@app.task()`（把它變成可派送的任務）。

一段一段看：

- **①②** 是在「準備要問什麼」。你可以想成填一張借書單：dataset 是「哪個書庫」、data_id 是「哪本書」、start/end 是「借閱期間」。
- **③ `requests.get(url, params=parameter)`** 是整段唯一真正跟外界互動的一行。它會組出像 `https://.../data?dataset=TaiwanStockPrice&data_id=2330&...` 這樣的網址並發出去。**注意：程式跑到這行會「等」網路回應，這段時間 CPU 其實在發呆。** 記住這個特性，第 6 章調併發時會用到。
- **④ `resp.json()`**：FinMind 回的是 JSON 文字，這行把它變成 Python dict，結構大概是 `{"msg": "...", "status": 200, "data": [ {...}, {...} ]}`。
- **⑤** 成功就把 `data["data"]`（一堆「每天一筆」的 dict）丟給 `pd.DataFrame` 變成表格印出；失敗就走 `else` 印出 `data["msg"]`。

> 小訣竅：如果你想看清楚 API 到底回什麼，暫時在 `resp.json()` 後面加一行 `print(data)`，先看原始結構，再看它變成 DataFrame 的樣子。

## 想再深入一點

- **這個任務是「I/O 密集」的典型**：整段最花時間的是 `requests.get` 等網路回應，CPU 幾乎在發呆。這種任務適合開「遠高於核心數」的併發（第 6 章會教 gevent）。
- **FinMind 免費版有請求上限**：沒登入時每小時請求數有限，抓太多會被擋。本章 5 支剛好；要大量抓可以去 FinMind 註冊拿 API token。
- **為什麼要先做一個「只印出」的版本？** 這是刻意的安排：先確認「任務能派送、worker 能收到、API 能呼叫、資料能解析」這條流程通了，第 4 章**再**加上寫資料庫。這樣萬一出錯，你能分辨是 Celery 的問題還是資料庫的問題。

## 卡住了？常見錯誤這樣排

| 你遇到的狀況 | 原因 | 怎麼解 |
|-------------|------|--------|
| worker 印出一行錯誤、不是表格 | API 回非 200（限流、參數錯）| 暫時加 `print(data)` 看原始回傳的 `msg` |
| 印出空的 DataFrame | 股票代碼錯，或那段期間沒資料 | 換一個確定有資料的代碼（如 2330）測試 |
| `requests` / `pandas` 找不到 | 套件沒裝 | 回根目錄 `uv sync` |
| 抓幾支就被擋 | FinMind 免費限流 | 減少數量，或註冊拿 token |

## 想一想（確認你懂了）

先自己想過再看答案。

**Q1：從第 1 章到這一章，你總共改了哪幾個檔案？哪些完全沒動？**

只改了兩個地方：換一支 producer（`producer_crawler_finmind_print.py`）、送出的任務換成 `crawler_finmind_print`。完全沒動的是：`worker.py`、worker 的啟動指令、broker（RabbitMQ）。這正是這一章要你體會的——Celery 的基礎設施跟任務內容是分開的。

**Q2：`crawler_finmind_print` 大部分時間花在「算」還是「等」？**

花在「等」。整段最慢的是 `requests.get` 等 FinMind 回應，這段時間 CPU 幾乎在發呆。這種「大部分時間在等」的任務叫 **I/O 密集**，跟「大部分時間在算」的 CPU 密集相反。記住這個判斷，第 6 章調 concurrency 時，I/O 密集的任務可以開遠高於核心數的併發。

**Q3：為什麼要特地做一個「只印出、不寫資料庫」的版本，而不是一步到位？**

為了把問題切開、方便除錯。先確認「任務能派送、worker 能收到、API 能呼叫、資料能解析」這條流程通了，第 4 章再加上寫資料庫。這樣萬一出錯，你能立刻分辨是 Celery 的問題還是資料庫的問題，而不是一堆東西攪在一起找不到原因。

**Q4：熱身段落的徒手呼叫，跟透過 Celery 派送，差在哪？**

做的事一模一樣（requests → json → DataFrame），差在「誰執行、能不能平行」。徒手版是你的終端機同步執行、一次一支；Celery 版是 worker 併發執行、5 支同時抓，而且之後可以排程自動跑、可以多開 worker 加速。這就是「把一段程式變成任務」換來的能力。
